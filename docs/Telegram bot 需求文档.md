# Telegram bot 需求文档

> 状态：草案 · 目标市场：俄罗斯（仅俄语 ru） · 收费：人工收款
> 本质：复用后端整套能力（Apify 抓取 → 规则引擎/AI 判词 → display JSON），入口从插件侧面板换成 Telegram 消息。

---

## 1. 目标

用户把 1688 商品链接发给 @Sourcely1688_bot，bot 调现有后端分析 API，把判词/评分/供应商信息渲染成俄语消息回给用户。

**一句话：一个后端 API + 两个前端（Chrome 插件 + Telegram bot）共用。**

| 层 | 归属 |
|----|------|
| 后端 | 共用，改 1 处（加 Telegram 鉴权通道），其余不动 |
| 插件前端 | 保留（Google 登录 + 多语言继续给插件用） |
| bot 前端 | 新增：轮询 + 渲染（只取 ru） |

---

## 2. 核心架构决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 后端 | 共用 `/api/analyze`，不拆 | 抓取/AI 判词/词库是全项目最贵部分，只写一份 |
| 契约 | **display JSON** 为通道无关契约 | 插件渲染 HTML，bot 渲染 Telegram 消息，各消费各的 |
| 异步 | bot 自己做「POST 拿 taskId → 轮询 → 拿 JSON」层 | 后端 20~60 秒才能出结果，天然异步，后端不改 |
| 语言 | 只渲染 ru | 目标市场俄罗斯；插件多语言保留 |
| 身份 | Telegram user_id（telegram_uid），零登录 | 不引入 Google OAuth，用户首次发言自动注册 |
| 收费 | 人工收款 | 俄区支付通道受限，MVP 最省事 |

---

## 3. 身份 / 会员 / 配额

一切挂在一个 `telegram_uid`（Telegram 数字 ID）上。

| 项 | 方案 |
|----|------|
| 身份 | 首次给 bot 发消息 → 后端按 `telegram_uid` 自动建用户，无密码无 OAuth |
| 会员等级 | 复用现有 `tier`（free / paid），付费 = 一次性 +300 配额，不限时间（无到期日） |
| 配额 | 复用限流机制，按 `telegram_uid` 记：free=3 次/天（每日重置）；付费 = 一次性 +300 次，每日不重置 |
| 判断入口 | `/api/analyze` 分析前查剩余配额，用完返回「配额用完」 |
| 历史记录 | 分析记录按 `telegram_uid` 归属，历史页按 uid 查 |

> 身份从后端拿，禁止 bot 传入 user_id（延续后端安全铁律：任何业务判断必须后端独立校验）。

---

## 4. 分析流程（异步）

```
用户发 1688 链接
  → bot 校验链接格式
  → POST 后端 /api/analyze 启动（拿 taskId）
  → bot 轮询（如 3 秒/次，最长 90 秒）
  → 拿到 display JSON（ru）
  → bot 渲染成俄语消息 + 按钮
  → 报告下方另发一条轻消息：今日剩余配额
```

---

## 5. 渲染契约

bot 从 display JSON 取以下字段渲染（全部取 ru 文本，glossary.json 已含 ru）：

| 卡片 | display 字段 | 内容 |
|------|-------------|------|
| 商品 | `title` / `price` / `productEval` | 名称、价格(低-高/起订量)、6 维评分 |
| 供应商 | `factory` / `supplierEval` | 源头/贸易商、年限、销量、星级、3 维评分 |
| 结论 | `summaryLine` | 综合结论 + 判词 |

约束：
- 单条消息 ≤ 4096 字符，超长拆多条
- 维度数据缺失 → 显示「无数据」灰色弱化（沿用 display JSON `na` 标记）
- 底部按钮走 Telegram Inline Keyboard

## 7. 用户场景流程

## 9. 后端改动清单（最小集）

| # | 改动 | 涉及 |
|---|------|------|
| 1 | telegram_uid ↔ 用户 映射（自动注册） | `repositories/user_repo.py` + 用户表 |
| 2 | 付费开通 = +300 配额（复用现有 `add_quota`，无需 expiry 字段） | `user_repo.py` |
| 3 | 配额按 telegram_uid 判断；付费 300 不受每日重置影响 | `domain/infra/rate_limiter.py` + `/api/analyze` 入口 |
| 4 | bot 专用鉴权通道（固定 bot token，绕开 Google JWT） | `middleware.py` 或 EXEMPT 白名单 + `config.py` |
| 5 | bot 轮询 + ru 渲染层（新进程/新服务） | 新增 `src/api/` 下 bot 模块 或独立 bot 服务 |

> 现有 Google 登录、插件多语言 **一律不动**（保留给插件）。

## 11. 风险与弊端

> 按严重度排序。均为可控项，无「架构走不通」级别风险。

| # | 风险 | 影响 | 等级 | 对策 |
|---|------|------|------|------|
| 1 | 多号薅免费配额 | bot 零门槛，TG 小号随便开，3次/天 形同虚设，白嫖 Apify/Qwen 成本 | 🔴 高 | free 不给次数只给 1 次体验；或新 uid 限流更狠；或接受默认亏损当获客成本 |
| 2 | 双鉴权 = 双攻击面 | Google JWT + bot token 两套校验逻辑，一处漏 = 全项目配额/用户体系被穿 | 🔴 高 | bot 鉴权走独立 bot token + telegram_uid 后端独立校验；安全边界写进测试 |
| 3 | 共享后端互相拖累 | 后端一重构，插件+bot 一起挂；bot 请求量大时异步任务堆积拖慢插件 | 🟠 中 | 后端回归测试覆盖两端；bot 轮询频率与并发做上限 |
| 4 | 契约被 bot 绑架 | display JSON 为插件设计，bot 需要额外字段时要么污染契约、要么 bot 侧硬适配 | 🟠 中 | 守住「后端只出 display JSON，bot 只消费不要求改」；缺字段在 bot 侧拼 |
| 5 | ru 判词质量不稳 | ru 走 Qwen 翻译（build_with_ai），Qwen 抖动 → bot 用户看到的判词不稳定，且 ru 未经过插件市场验证 | 🟠 中 | 上线前抽样核对 ru 判词；失败降级走 build_display() |
| 6 | bot 单点 + 运维 | bot 常驻进程挂了没人重启；新加坡直连 Telegram API 可能断线；同服务器挂了插件也挂 | 🟠 中 | systemd/supervisor 托管 + 日志；Telegram API 走 MTProto 代理兜底 |
| 7 | 用户表混存两类用户 | google email 字段对 bot 用户为空，查询统计要处理 null，历史/配额表多语言存储上涨 | 🟡 低 | schema 字段可空 + 按 uid 类型分区统计 |
| 8 | 人工收款转化率低 | USDT 对俄普通用户有门槛，付费路径全靠人工确认，时效差、易漏单 | 🟡 业务 | 收款说明写清楚；客服响应 SLA；后续可接 YooMoney 自动化 |
