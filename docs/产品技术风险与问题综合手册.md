## 第一部分：架构与风险决策类（25 项）

### 一、Apify 调用与缓存策略

#### 1. 同一链接重复调用浪费额度
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 前端每次分析都发起新的 Apify run，一次 $0.03-0.05，20-40 秒延迟 |
| 造成影响 | 成本线性浪费 + 用户重复等待 |
| 隐患 | 无后端缓存层，Apify 按次计费 |
| 解决方法 | **V1：** DB 持久化（`analysis` 表 `uk_offer_user` 唯一键，自动落库 `raw_json` + `display_i18n`），3.1 DB 检查命中即跳过 Apify，同用户同商品不重复抓取。**V2：** 多语言懒加载，从 raw 重建追加 `display_i18n`，无需重抓 |
| 切换时机 | 上 Redis 时一并切 |

#### 2. 并发请求同一链接导致重复调用（缓存击穿）
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 用户 A、B 同时搜同一商品 → 双方都调 Apify → 两份成本一份数据 |
| 造成影响 | 重复成本浪费 |
| 隐患 | 缓存写入非瞬时：查缓存为空→调 Apify→等结果→写缓存，此窗口期内的后续请求也查不到缓存 |
| 解决方法 | **V1：** 请求合并（Request Coalescing），`_pending: dict[str, asyncio.Task]`，同 offer_id 后续请求挂在同一 Task 上等结果（`services/analyze_svc.py:_pending`）。**V2：** 不变，单机字典优于分布式锁 |
| 切换时机 | 无需切换 ⚠️ *见第四部分「特别关注」1 — 该结论在多 worker 场景下不成立* |

#### 3. 缓存过期后数据变旧
| 字段 | 内容 |
|---|---|
| 等级 | 🟢 P3（V1.1） |
| 问题 | 1688 价格/库存会变，但自动刷新浪费额度 |
| 造成影响 | 数据新鲜度与成本的取舍 |
| 隐患 | 外部数据源新鲜度 vs 成本的经典 trade-off |
| 解决方法 | **V1：** TTL 30min 自动过期；V1.1 加「强制刷新」按钮 + 抓取时间戳展示。**V2：** 不变 |
| 切换时机 | V1.1 加强制刷新按钮即可 |

#### 4. Apify 调用超时
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | Apify 冷启动 + 爬取可能超过 60s，前端一直转圈，用户以为坏了 |
| 造成影响 | 用户体验受损，误以为服务故障 |
| 隐患 | 外部 API 延迟不可控 |
| 解决方法 | **V1：** 后端超时 90s，超时后有缓存（哪怕过期）返回缓存，无缓存返回明确错误；前端 2s 轮询，30s 后显示进度提示（`adapters/apify_adapter.py` + `services/analyze_svc.py:_run()`）。**V2：** 不变，90s 覆盖 95% 场景 |
| 切换时机 | 无需切换 |

#### 5. 1688 图片 CDN 在东南亚加载慢
| 字段 | 内容 |
|---|---|
| 等级 | 🟠 P1 |
| 问题 | 1688 CDN 国内部署，越南/印尼用户加载需 5-10s |
| 造成影响 | 海外目标用户首屏体验差 |
| 隐患 | CDN 地理位置不对 |
| 解决方法 | **V1：** `<img loading="lazy">` + 低分辨率占位图，最小改动先上线。**V2：** 后端代理下载 → 转存 OSS（阿里云新加坡节点）→ 前端用代理后 URL |
| 切换时机 | 东南亚真实用户反馈图片太慢时 |

#### 6. 恶意刷新与高频调用导致成本失控
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 脚本攻击或高频使用 → Apify 成本线性增长（单人次 $0.03 × 50 次/天 = $1.5/天 ≈ $45/月） |
| 造成影响 | 成本失控风险 |
| 隐患 | Apify 按次计费，服务端无调用次数上限 |
| 解决方法 | **V1：** 三层防御——L1 前端按钮防重（disabled 3s）；L2 offer_id 内存缓存（30min TTL，500 条 LRU）；L3 全局滑动窗口限流（30 次/分钟）。**V2：** 加 L4 IP 日限（Redis `INCR ip:date` + `EXPIRE 86400`） |
| 切换时机 | 上 Redis 时 |
| ⚠️ 待复核 | L3 若为全局共享计数（非按 IP/用户维度），存在"一人刷爆、误伤全体"的设计风险，需确认限流 key 维度 |

### 二、判词引擎

#### 7. 判词覆盖率不足
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 规则引擎穷举不了所有产品类型，只写少量规则则大量产品无判词 |
| 造成影响 | 部分产品无法生成有效判词 |
| 隐患 | V1 不用 LLM，规则引擎能力有上限 |
| 解决方法 | **V1：** 三层规则金字塔——L1 精确匹配（~40%）+ L2 区间匹配（~40%）+ L3 通用兜底（~20%），目标 L1+L2 覆盖 80%。**V2：** LLM 增强，前置条件为规则引擎跑 ≥ 6 个月 + 查询历史 ≥ 5000 条 |
| 切换时机 | 满足 V2 前置条件 + 用户反馈规则引擎覆盖不足 |

#### 8. 判词闪烁（阈值附近波动）
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 回头率 70.1%→69.9% 导致判词在"高回头率"/"回头率一般"间跳变，用户刷新看到不一致，误以为系统不稳定 |
| 造成影响 | 用户对系统稳定性的信任受损 |
| 隐患 | 精确阈值无缓冲区间 |
| 解决方法 | **V1：** 滞回区间（Hysteresis），触发阈值 >70%，回落阈值 <65%，65-70% 间不触发变化。**V2：** 不变，经典控制理论方案 |
| 切换时机 | 无需切换 |

#### 9. 判词模板配置化
| 字段 | 内容 |
|---|---|
| 等级 | 🟡 P2（已落地） |
| 问题 | 判词硬编码在 Python，新增品类需改代码、测试、发版 |
| 造成影响 | 迭代成本高 |
| 隐患 | 业务规则和代码未分离 |
| 解决方法 | **V1：** 已落地，JSON 配置文件 `domain/verdict_templates.json`，新增品类只加配置不动代码。**V2：** 加多语言字段（中/英/越/泰），同文件扩展 |
| 切换时机 | V1.1 多语言时 |

#### 10. 判词依赖的核心字段缺失
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | Apify 数据不完整，判词规则依赖字段为 null，引擎报错或判词空 |
| 造成影响 | 分析结果异常/报错 |
| 隐患 | 外部数据质量不可控 |
| 解决方法 | **V1：** 判词引擎只依赖核心字段，计算前检查存在性，核心缺失走 L3 兜底，非核心缺失不影响。**V2：** 不变 |
| 切换时机 | 无需切换 |

#### 11. 判词双引擎同步
| 字段 | 内容 |
|---|---|
| 等级 | 🟠 P1（持续关注） |
| 问题 | 判词逻辑在 `verdict_engine.py`（后端）和 `report.js`（前端）各实现一套，改一处不改另一处会导致判词不一致 |
| 造成影响 | 前后端判词不一致，用户信任崩塌 |
| 隐患 | 两套引擎场景不可替代——后端服务 API + 历史页；前端服务 sample JSON 静态模式 |
| 解决方法 | **同步铁律：** ①改判词规则必须两处同步 ②两文件顶行均有同步铁律注释 ③改完 grep 两端同名函数/变量确认一致。**V2：** 若 sample 模式不再需要前端判词，可删前端引擎 |
| 切换时机 | sample JSON 改成后端预生成时 |
| ⚠️ 待复核 | 现有单元测试仅分别验证 `product_mapper.py`/`verdict_engine.py` 自身正确性，**未验证前后端跨语言输出一致性**，"铁律"目前仍依赖人工遵守，建议补跨语言一致性测试用例集 |

#### 12. 判词和数据映射改坏了没人知道（已解决）
| 字段 | 内容 |
|---|---|
| 等级 | 🟡 P2（已落地） |
| 问题 | `product_mapper.py` + `verdict_engine.py` 是核心纯函数，改一行只能手动验证 |
| 造成影响 | 改动风险不可控 |
| 隐患 | 无自动化回归保障 |
| 解决方法 | **V1：** 单元测试安全网，`tests/test_product_mapper.py`（12 用例）+ `tests/test_verdict_engine.py`（18 用例），<0.1s 跑完。**V2：** 每次改这俩文件必须跑测试，CI 集成 |
| 切换时机 | 上 CI 时 |

### 三、异常状态处理

#### 13. Apify 返回空数据
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 链接无效、下架、反爬导致无数据，用户不知道发生了什么 |
| 造成影响 | 用户困惑、体验中断 |
| 隐患 | 外部数据源不可靠 |
| 解决方法 | **V1：** 三级降级响应——一级（有缓存）返回缓存 + 黄色警告；二级（无缓存+可识别原因）明确错误+建议动作；三级（无缓存+原因不明）通用错误+客服入口。**V2：** 不变 |
| 切换时机 | 无需切换 |

#### 14. Apify 返回部分数据（字段缺失）
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 页面结构变化导致某字段缺失，不能因一个字段 null 让整个页面崩溃 |
| 造成影响 | 页面渲染异常 |
| 隐患 | 外部 JSON schema 不稳定 |
| 解决方法 | **V1：** 前端字段级容错——核心字段缺失走 L3 兜底判词，非核心字段缺失静默隐藏，所有渲染前 null check。**V2：** 不变 |
| 切换时机 | 无需切换 |

#### 15. 用户输入非 1688 链接
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 淘宝/拼多多/乱码链接穿透到 Apify，浪费额度 |
| 造成影响 | 成本浪费 |
| 隐患 | 用户行为不可控 |
| 解决方法 | **V1：** 前端正则 + 后端 offerId 校验，双重拦截。**V2：** 不变 |
| 切换时机 | 无需切换 |

#### 16. 后端自己挂了
| 字段 | 内容 |
|---|---|
| 等级 | 🟠 P1 |
| 问题 | 进程崩溃导致用户不可用，且没人知道 |
| 造成影响 | 服务中断且无感知，故障发现滞后 |
| 隐患 | 单机部署无自动恢复 |
| 解决方法 | **V1：** `/health` endpoint + Supervisor/systemd `restart=always` + 日志写文件。**V2：** 容器化部署（Docker）+ K8s liveness probe，V1 日活低暂不需要 |
| 切换时机 | 用户量上来 / 需要多机部署时 |
| ⚠️ 待复核 | 问题标题强调"没人知道"，但 V1 方案只解决了"崩溃后自动重启"，**未配套任何主动告警机制**，日志写文件≠有人会看，建议加低成本的外部心跳监控（如探活服务 + IM/邮件告警） |

### 四、性能与加载体验

#### 17. 用户等 20-40 秒什么也看不到
| 字段 | 内容 |
|---|---|
| 等级 | 🔴 P0 |
| 问题 | 同步阻塞等待导致 HTTP hang 住，前端白屏，用户关页面 |
| 造成影响 | 用户流失 |
| 隐患 | Apify 是长耗时操作，不能同步等待 |
| 解决方法 | **V1：** 异步轮询（参考 OpenAI / Midjourney），POST 立即返回 task_id，前端 2s 轮询 `GET /task/{id}`，骨架屏 + 进度提示；不采用 SSE/WebSocket（杀鸡用牛刀）。**V2：** 不变，轮询是行业标准 |
| 切换时机 | 无需切换 |

#### 18. 轮询时用户切走页面再回来
| 字段 | 内容 |
|---|---|
| 等级 | 🟡 P2 |
| 问题 | 锁屏、切微信导致轮询停止，结果丢失 |
| 造成影响 | 移动端体验受损 |
| 隐患 | 移动端多任务切换导致前端状态丢失 |
| 解决方法 | **V1：** task_id 存 sessionStorage，页面加载时检查未完成任务并恢复轮询，后端保活 30min。**V2：** 不变 |
| 切换时机 | 无需切换 |

#### 19. 首屏资源体积过大
| 字段 | 内容 |
|---|---|
| 等级 | 🟠 P1 |
| 问题 | CSS/JS/字体过大，东南亚 4G 网络加载慢 |
| 造成影响 | 首屏加载慢，海外用户流失风险 |
| 隐患 | 前端资源未做体积控制 |
| 解决方法 | **V1：** CSS 变量系统 ~2KB + JS 按页拆分 + 系统字体栈（不用 Web Font），目标首屏 <200KB。**V2：** 不变，200KB 为长期目标 |
| 切换时机 | 引入新功能时持续检查 |

## 第四部分：特别关注 — 待复核 / 内部矛盾项

以下几项是本次合并整理时发现的**文档内部矛盾或结论错误**，建议在下一次迭代排期前优先复核，避免带着错误假设继续开发。

### 1. 🔴 【安全】Open Redirect 修复自评存在逻辑错误（对应 Bug #11）

文档写"`//evil.com` 不含 `://` 但也不以 `/` 开头，第一条就拦住了"——这个判断**是错的**：`//evil.com` 的首字符就是 `/`，会通过 `startswith('/')` 校验。若实际代码逻辑确实是 `redirect.startswith('/') and '://' not in redirect`，Open Redirect 漏洞可能仍未修复。**建议立即回代码验证**，并补充 `not redirect.startswith('//')` 或改用 `urlparse().netloc` 判空的更彻底方案。

### 2. 🟡 【架构一致性】请求合并（Coalescing）与"上 Redis / 多 worker"路径矛盾

风险清单认为 Coalescing "V2 不变"，但同一文档又把"开多 worker"列为触发 Redis 迁移的信号之一。多 worker 场景下单进程内存里的 `_pending` 字典在跨进程之间互不知情，Coalescing 会失效。建议明确标注该方案的**单进程适用边界**，并在 Redis 迁移计划中一并评估分布式锁或接受短暂重复调用的取舍。

### 3. 🟡 【设计】全局限流可能"误伤"正常用户

L3 全局滑动窗口限流（30 次/分钟）如果是所有用户共享同一计数桶，一人刷爆即可导致其他正常用户被限流。建议确认限流 key 的维度（全局 vs 按 IP/用户），如为全局，建议改造为分维度限流。

### 4. 🟡 【测试覆盖盲区】判词双引擎"同步铁律"缺自动化保障

现有单元测试仅验证 `product_mapper.py`/`verdict_engine.py`（后端）各自的正确性，**未验证前端 `report.js` 与后端判词逻辑的跨语言一致性**。建议补一份固定输入+期望输出的跨语言一致性测试集，纳入 CI。

### 5. 🟡 【问题描述与方案不匹配】"后端挂了没人知道"未被真正解决

V1 方案只解决了自动重启，未配套任何主动告警。建议加一个低成本的外部心跳探活 + 告警（如探活服务 + IM/邮件通知）。

### 6. 🟢 【能力边界未讲清】匿名用户状态方案无法跨设备/跨浏览器同步

这是 sessionStorage 方案的固有限制而非"边缘风险"，建议在产品文档中明确标注，避免后续被误报为 bug。

### 7. 🟢 【遗漏项】数据库备份/灾难恢复策略缺失

当前文档聚焦于"进程崩溃自动重启"，但未见任何关于 MySQL 定期备份的条目。数据丢失是比进程重启更严重且不可逆的风险，建议补充一条到风险清单并明确责任人和执行频率。
