# 代码质量流程 — 改前影响面分析

> 生命周期：已定稿 | 目的：在写代码前拦住静态逻辑问题。固化为 `/pre-flight` Skill，本文档为方法论依据。
>
> **CLAUDE.md 触发规则：每次代码改动前，回答两个问题：①有没有替换/废弃旧东西？②涉及几个文件？→ 有替换或 ≥2 文件 → 运行 `/pre-flight`。**

---

## 一、核心洞察：bug 不是随机的，是 4 类

| 类别 | 特征 | 拦法 | 成本 |
|------|------|------|------|
| **A. 替换不干净** | 用 B 替 A，A 的残留引用/标记/行为没清干净 | grep 旧符号全项目 → 逐点确认 | 中 |
| **B. 重复工作** | 同一资源加载两次、同一计算跑两次 | grep 新符号 → 确认是否已有 | 低 |
| **C. 新功能缺胳膊** | 功能能跑，但缺配套（超时/监控/上限/持久化） | 对照"功能完整性清单"自查 | 低 |
| **D. 外部依赖假设** | 假设外部系统正常，没做防御 | 对照"防御性编程清单"自查 | 低 |

**这 4 类不依赖具体项目。任何项目、任何语言的 bug 都逃不出。**

---

## 二、流程树（一步定性）

```
收到需求
  │
  ▼
一问："这次有没有替换/废弃旧东西？"
（旧函数、旧模块、旧字段名、旧标记、旧流程）
  │
  ├── 有替换 ──→ 🔴 全流程
  │               ├─ grep 旧符号全项目 → 逐点确认残留
  │               ├─ 对照"功能完整性清单"
  │               ├─ 对照"防御性编程清单"
  │               ├─ 写单点测试（happy + 异常 + 边界）
  │               ├─ 改代码 → 跑测试
  │               └─ /code-review + /security-review
  │
  └── 无替换 ──→ 新增还是修改？
        │
        ├── 纯新增（不碰旧代码）
        │     ├─ 涉及外部 API/计费/持久化？ → 🟡
        │     │     ├─ grep 新符号（防重复）
        │     │     ├─ 对照"功能完整性清单"
        │     │     ├─ 写单点测试（happy path）
        │     │     └─ /code-review
        │     │
        │     └─ 纯逻辑/UI/常量？ → 🟢
        │           直接写，改完点一下。零额外成本。
        │
        └── 修改现有逻辑
              ├─ 改的是外部 API/认证/持久化？ → 🔴 全流程
              └─ 改的是内部逻辑/展示/常量？ → 🟡
                    ├─ grep 函数名（找调用方）
                    ├─ 对照"防御性编程清单"
                    ├─ 写单点测试（happy path）
                    └─ /code-review + 手动走流程
```

## 三、两张清单

### 功能完整性清单（C 类 — 新增功能时用）

| 新增了什么 | 必须检查 |
|-----------|---------|
| 外部 API 调用 | 超时设了？异常降级了？调用次数/成功率的日志？ |
| 缓存 | TTL 设了？淘汰机制？容量上限？ |
| 内部标记字段 | 持久化条件检查？上游设置点、下游清理点一致？ |
| Prompt/模板 | 输出格式校验？token 上限？ |
| 新模块/文件 | 是否已有模块干了类似的事？（grep 同名/同功能） |

### 防御性编程清单（D 类 — 敏感层改动时用）

| 风险 | 必须检查 |
|------|---------|
| 外部挂了 | 每个外部调用有降级路径？降级后用户能感知吗？ |
| 数据泄漏 | 新字段会出现在前端 JSON 里吗？该脱敏吗？ |
| 资源泄漏 | 新创建的 task/timer/cache 有清理机制吗？ |
| 无界增长 | for/while 有退出条件？list/dict 有容量上限？ |
| 并发冲突 | 新加的全局可变容器有去重或锁吗？ |

## 四、测试卡点（Skill 强制执行）

| 级别 | 测试要求 | Skill 行为 |
|------|---------|-----------|
| 🟢 | 无需 | 直接放行 |
| 🟡 | 1 个单点测试（happy path 脚本） | 提示"建议先写测试" → 用户选写/跳过 → 标记 |
| 🔴 | 3 个单点测试（happy + 异常 + 边界） | 强制暂停 → 用户写测试或明确说跳过 → 标记 |

**当前阶段用裸脚本，不引入 pytest 框架。** 测试脚本放 `tests/` 目录，积累到 ≥5 个后再评估用 pytest 统一。

## 五、Token 预估（加权平均）

| 级别 | 占比 | 额外 token | 加权 |
|------|------|-----------|------|
| 🟢 轻 | ~50% | 0 | 0 |
| 🟡 中 | ~30% | +5k | +1.5k |
| 🔴 重 | ~20% | +15k | +3k |
| **平均** | | | **+4.5k** |

**对比：修一个事后发现的 bug 平均 ~30k token。** 流程本身是省的。

## 六、已知局限

| 拦不住 | 为什么 | 怎么办 |
|--------|--------|--------|
| 领域逻辑错误 | 需要懂业务 | 智囊团讨论 + 人工测试 |
| 运行时竞态 | grep 看不见并发 | 出问题走 `/systematic-debugging` |
| 外部 API 行为变化 | 不在代码里 | 监控告警（未来迭代） |
| 设计层面做错了 | 流程管"有没有遗漏"，不管"有没有做对" | 智囊团在设计阶段拦 |
| 🟢 级别改出问题 | 没有检查机制 | 用户自己点一下发现 |

---

## 七、持续改进

每次出一个漏网的 bug → 问：属于 A/B/C/D 哪类？清单里有没有这条？没有 → 补。**清单不超过 5 条，旧的顶出去。** 不让清单膨胀。
