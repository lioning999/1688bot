## 一、决策：继续完善，不重新开发

**判断依据：** 已发现的隐患（G1-G4）没有一个是「架构错误」，全是「实现细节的坑」——漏了锁、漏了判断、死常量、漏退配额。每个都是几行到几十行的局部修复。

**不重写的原因：**

1. 架构是对的：五层分层、异步轮询、DB 持久化、多语言管线，设计方向全对。
2. 功能已完整：登录/分析/历史/收藏/配额/多语言/插件都做了，重写等于全部重做。
3. 重写会丢掉已调对的正确逻辑（mapper 容错、judge 降级链、Qwen 翻译降级），并犯同样性质的新错。

## 二、修复原则（怎么改不出问题）

> 上次出问题的根子不是「不够小心」，是「没测试兜底 + 一次改太多」。所以靠流程，不靠小心。

| # | 原则 | 说明 |
|---|------|------|
| 1 | **先看清再修** | 排查完所有节点、隐患清单列全、看关联，再动手。不看清就动，一定返工 |
| 2 | **最小改动** | 一个 bug 只改一处，不顺手改无关代码（铁律一）。G1 加锁就只加锁 |
| 3 | **改前 grep 影响面** | 改函数签名/字段/常量前，grep 全项目调用方，确认不误伤 |
| 4 | **补测试兜底** | 核心路径写测试（见第四节）。以后每次改动跑一遍就知道破没破 |
| 5 | **分批次小步 commit** | 按 🔴→🟡 修，一批一个 commit 做检查点，出问题可回退 |
| 6 | **修完实测** | 真实跑 1688 链接走完 4 语言 + DB 命中 + 失败重试 |
