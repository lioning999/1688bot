## 一、Apify 调用与缓存策略

### 问题 1：同一链接重复调用浪费额度

**问题：** 前端每次分析都发起新的 Apify run，一次 $0.03-0.05，20-40 秒延迟。

**根因：** 无后端缓存层。Apify 按次计费。

**V1 方案：** Python dict 内存缓存，`offerId → 结果 JSON`，TTL 30min，LRU 500 条上限。实现：`domain/cache.py`。

**V2 方案：** 切 Redis。`GET offer:{id}` + `EXPIRE 1800`。跨进程共享，重启不丢。

**切换时机：** 上 Redis 时一并切（见 §七 问题 3）。

---

### 问题 2：并发请求同一链接导致重复调用（缓存击穿）

**问题：** 用户 A 和 B 同时搜同一商品 → 双方都调 Apify → 两份成本一份数据。

**根因：** 缓存写入不是瞬间的。查缓存为空 → 调 Apify → 等结果 → 写缓存。这个窗口期内后来的请求也查不到缓存。

**V1 方案：** 请求合并（Request Coalescing）。`_pending: dict[str, asyncio.Task]`，同 offer_id 的后续请求挂在同一个 Task 上等结果。实现：`services/analyze_svc.py:_pending`。

**V2 方案：** 不变。单机字典在此场景优于分布式锁。

**切换时机：** 无需切换。

---

### 问题 3：缓存过期后数据变旧

**问题：** 1688 价格/库存会变，但自动刷新浪费额度。

**根因：** 外部数据源，缓存新鲜度 vs 成本的经典 trade-off。

**V1 方案：** TTL 30min 自动过期。V1.1 加「强制刷新」按钮 + 数据抓取时间戳展示。

**V2 方案：** 不变。业务验证过的 TTL 不需要调。

**切换时机：** V1.1 加强制刷新按钮即可。

---

### 问题 4：Apify 调用超时

**问题：** Apify 冷启动 + 爬取可能超过 60s → 前端一直转圈 → 用户以为坏了。

**根因：** 外部 API 延迟不可控。

**V1 方案：** 后端超时 90s。超时后有缓存（哪怕过期）返回缓存；无缓存返回明确错误。前端 2s 轮询，30s 后显示进度提示。实现：`adapters/apify_adapter.py` + `services/analyze_svc.py:_run()`。

**V2 方案：** 不变。90s 覆盖 95% 场景。

**切换时机：** 无需切换。

---

### 问题 5：1688 图片 CDN 在东南亚加载慢

**问题：** 1688 CDN 国内部署，越南/印尼用户 5-10s 加载。

**根因：** CDN 地理位置不对。

**V1 方案：** `<img loading="lazy">` + 低分辨率占位图。最小改动先上线。

**V2 方案：** 后端代理下载 → 转存 OSS（阿里云新加坡节点）→ 前端用代理后 URL。

**切换时机：** 东南亚真实用户反馈图片太慢时。

---

### 问题 6：恶意刷新与高频调用导致成本失控

**问题：** 脚本攻击或高频使用 → Apify 成本线性增长（单人次 $0.03 × 50 次/天 = $1.5/天 = $45/月）。

**根因：** Apify 按次计费，没有服务端调用次数上限。

**V1 方案：** 三层防御体系：

| 层 | 方案 | 参数 | 防什么 |
|----|------|------|--------|
| L1 前端 | 按钮 loading 防重 | disabled 3s | 手抖重复点 |
| L2 缓存 | offer_id 内存缓存 | 30min TTL，500 条 LRU | 同一商品重复搜 |
| L3 全局 | 滑动窗口全局限流 | 30 次/分钟 | 脚本攻击兜底 |

**V2 方案：** 加 L4——IP 日限（Redis `INCR ip:date` + `EXPIRE 86400`）。

**切换时机：** 上 Redis 时。

## 二、判词引擎

### 问题 1：判词覆盖率不足

**问题：** 规则引擎穷举不了所有产品类型。只写 10 条规则 → 大量产品无判词。

**根因：** V1 不用 LLM（§九），规则引擎能力有上限。

**V1 方案：** 三层规则金字塔——L1 精确匹配（~40%）+ L2 区间匹配（~40%）+ L3 通用兜底（~20%）。目标 L1+L2 覆盖 80%。

**V2 方案：** LLM 增强。前置条件：规则引擎跑 ≥ 6 个月 + 查询历史 ≥ 5000 条。

**切换时机：** 满足 V2 前置条件 + 用户反馈规则引擎覆盖不足。

---

### 问题 2：判词闪烁（阈值附近波动）

**问题：** 回头率 70.1%→69.9% → 判词从"高回头率"变"回头率一般" → 用户刷新看到不一样 → 以为系统不稳定。

**根因：** 精确阈值无缓冲区间。

**V1 方案：** 滞回区间（Hysteresis）。触发阈值 > 70%，回落阈值 < 65%。65-70% 间不触发变化。

**V2 方案：** 不变。经典控制理论方案。

**切换时机：** 无需切换。

---

### 问题 3：判词模板配置化

**问题：** 判词硬编码在 Python。新增品类 → 改代码 → 测试 → 发版。

**根因：** 业务规则和代码未分离。

**V1 方案：** 已落地——JSON 配置文件 `domain/verdict_templates.json`。新增品类只加配置不动代码。

**V2 方案：** 加多语言字段（中/英/越/泰），同文件扩展。

**切换时机：** V1.1 多语言时。

---

### 问题 4：判词依赖的核心字段缺失

**问题：** Apify 数据不完整 → 判词规则依赖字段为 null → 引擎报错或判词空。

**根因：** 外部数据质量不可控。

**V1 方案：** 判词引擎只依赖核心字段，计算前检查存在性。核心缺失 → L3 兜底。非核心缺失 → 不影响。

**V2 方案：** 不变。

**切换时机：** 无需切换。

---

### 问题 5：判词双引擎同步（⚡ 2026-07-23）

**问题：** 判词逻辑在 `verdict_engine.py`（后端）和 `report.js`（前端）各实现一套。改一处不改另一处 → 判词不一致 → 信任崩塌。

**根因：** 两套引擎场景不可替代——后端服务 API + 历史页；前端服务 sample JSON 静态模式。

**同步铁律：**
1. 改判词规则必须两处同步（CLAUDE.md §四 第 7 项已覆盖）
2. 两文件顶行均有 `⚠️ 同步铁律` 注释
3. 改完 grep 两端同名函数/变量确认一致

**V2 方案：** 如果 sample 模式不再需要前端判词（sample JSON 预计算好），可删前端引擎。

**切换时机：** sample JSON 改成后端预生成时。

---

### 问题 6：判词和数据映射改坏了没人知道（⚡ 2026-07-23 已解决）

**问题：** `product_mapper.py` + `verdict_engine.py` 是核心纯函数，改一行只能手动验证。

**V1 方案：** 单元测试安全网。`tests/test_product_mapper.py`（12 用例）+ `tests/test_verdict_engine.py`（18 用例），<0.1s 跑完。

**V2 方案：** 每次改这俩文件必须跑测试。CI 集成。

**切换时机：** 上 CI 时。

## 三、异常状态处理

### 问题 1：Apify 返回空数据

**问题：** 链接无效、下架、反爬 → 无数据 → 用户不知道发生了什么。

**根因：** 外部数据源不可靠。

**V1 方案：** 三级降级响应：

| 级别 | 条件 | 响应 |
|------|------|------|
| 一级 | 有缓存（哪怕过期） | 返回缓存 + 黄色警告 |
| 二级 | 无缓存 + 可识别原因 | 明确错误 + 建议动作 |
| 三级 | 无缓存 + 原因不明 | 通用错误 + 客服入口 |

**V2 方案：** 不变。

**切换时机：** 无需切换。

---

### 问题 2：Apify 返回部分数据（字段缺失）

**问题：** 页面结构变化 → 某字段缺失 → 不能因一个字段 null 让整个页面崩。

**根因：** 外部 JSON schema 不稳定。

**V1 方案：** 前端字段级容错——核心字段缺 → L3 兜底判词；非核心缺 → 静默隐藏；所有渲染前 null check。

**V2 方案：** 不变。

**切换时机：** 无需切换。

---

### 问题 3：用户输入非 1688 链接

**问题：** 淘宝/拼多多/乱码 → 穿透到 Apify → 浪费额度。

**根因：** 用户行为不可控。

**V1 方案：** 前端正则 + 后端 offerId 校验，双重拦截。

**V2 方案：** 不变。

**切换时机：** 无需切换。

---

### 问题 4：后端自己挂了

**问题：** 进程崩溃 → 用户不可用 → 没人知道。

**根因：** 单机部署无自动恢复。

**V1 方案：** `/health` endpoint + Supervisor/systemd `restart=always` + 日志写文件。

**V2 方案：** 容器化部署（Docker）+ K8s liveness probe。但 V1 日活低不需要。

**切换时机：** 用户量上来 / 需要多机部署时。

## 四、性能与加载体验

### 问题 1：用户等 20-40 秒什么也看不到

**问题：** 同步阻塞等待 → HTTP hang 住 → 前端白屏 → 用户关页面。

**根因：** Apify 是长耗时操作，不能同步等待。

**V1 方案：** 异步轮询（参考 OpenAI / Midjourney）。POST 立即返回 task_id → 前端 2s 轮询 GET /task/{id} → 骨架屏 + 进度提示。不推荐 SSE/WebSocket——杀鸡用牛刀。

**V2 方案：** 不变。轮询是行业标准。

**切换时机：** 无需切换。

---

### 问题 2：轮询时用户切走页面再回来

**问题：** 锁屏、切微信 → 轮询停了 → 结果丢了。

**根因：** 移动端多任务切换导致前端状态丢失。

**V1 方案：** task_id 存 sessionStorage。页面加载时检查未完成任务 → 恢复轮询。后端保活 30min。

**V2 方案：** 不变。

**切换时机：** 无需切换。

---

### 问题 3：首屏资源体积过大

**问题：** CSS/JS/字体过大 → 东南亚 4G 慢。

**根因：** 前端资源未做体积控制。

**V1 方案：** CSS 变量系统 ~2KB + JS 按页拆分 + 系统字体栈（不要 Web Font）。目标首屏 < 200KB。

**V2 方案：** 不变。200KB 阈值是长期目标。

**切换时机：** 引入新功能时持续检查。

## 七、服务稳定性

### 问题 1：日志与监控缺失

**问题：** 出问题后不知道发生了什么。

**V1 方案：** 关键节点打日志（请求到达→缓存命中/未命中→Apify 开始/结束/超时→响应返回）。V1 tail 日志即可，不上 Prometheus/Grafana。

**V2 方案：** 接入监控平台。切换时机：日活 > 100。

---

### 问题 2：依赖 Apify 单点故障

**问题：** Apify 挂了 → 产品不可用。

**根因：** 外部依赖，不可控。

**V1 方案：** 接受风险。做好三件事：①明确错误信息 ②缓存兜底 ③客服入口。

**V2 方案：** 不接备用爬虫（成本太高）。做好降级即可。

---

### 问题 3：纯内存存储 — 无持久化、多进程不共享（⚡ 2026-07-24）

**问题：** 4 个核心结构全是 Python dict/deque，存在三个通用隐患：

| 隐患 | 影响 |
|------|------|
| 进程重启 → 全丢 | 缓存、配额、任务状态全部清零 |
| 多 worker 各自独立 | 配额各算各的，形同虚设 |
| 无上限无清理（部分） | 僵尸数据永久驻留内存 |

**根因：** JWT 无状态架构。没有 Redis 或任何进程外存储。

**当前状态：**

| 结构 | 文件 | 清理 | 上限 | 问题 |
|------|------|------|------|------|
| `_daily_counter` | `routes/analyze.py` | ❌ | ❌ | 过期 key 不删，多进程不共享 |
| `cache` | `domain/cache.py` | ✅ LRU | ✅ 500 | 多进程不共享 |
| `_timestamps` | `domain/rate_limiter.py` | ✅ pop 过期 | ✅ 30 | 多进程不共享 |
| `_tasks` | `services/analyze_svc.py` | ✅ TTL 惰性 | ❌ | 多进程不共享 |

**V1 方案：** 单进程运行。`_check_quota` 加惰性清理过期 key（10min）。接受重启丢数据。

**V2 方案：** 上 Redis。所有 dict → Redis。`INCR` + `EXPIRE` 做配额，`GET`/`SET` + `EXPIRE` 做缓存，`SADD`/`SREM` 做任务。多进程天然共享，重启不丢。

**切换时机：** 三个信号任意一个触发——开多 worker / 日活上来频繁发布 / 加第二台机器。

**成本：** 接口签名已对齐（`get/set` 语义），改 2 个文件约 2h。

## 八、数据库与历史存储

### 核心决策：存，但只存元数据（方案 B，2026-07-21）

**问题：** 用户想回看之前的查询。

**方案对比：**

| | A：不存 | B：存元数据 ✅ | C：存完整 JSON |
|---|---|---|---|
| 内容 | 无 | offerId + 标题 + 价格 + 图片 + 时间 | B + Apify 原始 JSON |
| 行大小 | 0 | ~2KB | ~50KB |
| 回看体验 | 无 | 看列表，点进去走缓存 | 离线可看 |
| 数据新鲜度 | 总是最新 | 依赖缓存 | 可能过期 |

**V1 方案：** B。`analysis` 表 + 子表（spec/sku/price_tier）。用户手动保存才写入 DB。

**V2 优化：** 不做收藏/对比/分页/完整 JSON 存储。需要数据积累后再排。

## 九、AI 决策：V1 零 AI

### 核心决策：V1 不使用任何 LLM

**三处可能用 AI 的位置及排期：**

| 位置 | V1 方案 | V2 演进 | 前置条件 |
|------|---------|---------|---------|
| 判词生成 | 规则引擎三层 | LLM 增强 | 规则引擎跑 ≥ 6 月 + 数据积累 |
| 产品翻译 | 中英手动模板 | DeepL / LLM | 翻译准确率 ≥ 95% 验收 |
| 智能推荐 | 不做 | LLM 推荐 | 查询历史 ≥ 5000 条 |

**V1 不用 AI 的理由：**
- 规则引擎覆盖 80% 场景，零成本，零延迟，不幻觉
- 翻译质量不可控（专业术语：不锈钢/冷轧板）
- 推荐无数据基础

**V2 引入 AI 的前置条件：**
- 规则引擎稳定运行 ≥ 6 月
- 查询历史 ≥ 5000 条
- LLM 判词标注"AI 生成，仅供参考"
- 翻译准确率 ≥ 95% 验收标准

**产品定位：** V1 = 数据展示 + 规则引擎产品。V2 = AI 产品。

## 十、匿名用户状态与登录关联（⚡ 2026-07-24 新增）

### 问题：未登录时看到分析结果 → 点保存 → 跳 Google 登录 → 回来后数据丢了

**完整链路（8 个环节）：**

```
分析完成 → sessionStorage 暂存结果 → OAuth state 带 return URL
→ Google 回调 → 后端解析 state → 重定向回 report 页
→ initAuth() 取 token → 页面读 sessionStorage 恢复 → 秒出数据
```

### 根因：JWT 无状态架构

JWT 的设计哲学是服务端不记状态——这恰好和"未登录→登录后关联"的需求矛盾。

大网站（GitHub、Twitter、YouTube）的做法：**Session + JWT 混合。**
- 每个访客发 session cookie（UUID）
- 匿名动作存在服务端，按 session_id 绑定
- 登录后 session 升级绑定 user_id → 匿名数据自动合并

我们做不到——没有 Redis、没有 session 基础设施、JWT 是唯一身份机制。

### V1 方案：sessionStorage + OAuth state

**前端暂存结果 + OAuth state 带回跳路径，回来后从 sessionStorage 恢复渲染。**

| 环节 | 实现 | 已知风险 |
|------|------|---------|
| 暂存 | `sessionStorage.setItem('lastResult_' + offerId, data)` | sessionStorage 仅在当前标签页 |
| 跳转 | `/api/auth/google/login?redirect=...` → state 编码 | state 未 URL 编码会断（已修） |
| 回调 | 后端解析 state → `/report.html?offerId=xxx&token=...` | — |
| URL 清洗 | `initAuth()` 只删 token/user，保留 offerId | 以前抹掉全部 query（已修） |
| 恢复 | 页面 load → 查 sessionStorage → 命中秒渲染 | 隐私模式 / 部分浏览器可能丢 |

**兜底：** 如果 sessionStorage 恢复失败 → 走正常 API 分析 → 缓存命中 30min 内秒返。

### V2 方案：Session + JWT 混合 + Redis

```
1. 后端给每个访客发 session cookie（UUID）
2. 匿名分析结果暂存 Redis：key = "anon:{session_id}:{offer_id}", TTL 24h
3. 用户登录 → session_id 不变 → 后端升级 session 绑定 user_id
4. 匿名数据自动合并到用户账户
5. Redis 同时接管配额计数（INCR + EXPIRE）
```

### 切换时机

**上 Redis 时一并实施。** Session + Redis + 配额 三个需求同一天解决，底层依赖都是 Redis。

### 不可替代性

V1 方案是 JWT-only 架构下的最优折衷。没有 session 基础设施，无法在不引入 Redis 的前提下实现匿名→登录的数据关联。
