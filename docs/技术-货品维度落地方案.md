## 一、翻译归属

**全部走 📖 glossary（term_glossary.json），不走 i18n，不走 Qwen。**

原因：evaluator 输出的每个字都是"中文由我们产出、可穷举"——这是 glossary 的触发条件。

| 输出 | 翻译层 | 原因 |
|:--|:--|:--|
| 标签 `🔥热销品` | 📖 glossary | 固定4条，我们定义 |
| 数据行 `月销8900+` | 📖 glossary（前缀）+ ➖ 不译（数字） | "月销"是固定前缀，数字无语言 |
| 人话 `市场反复验证...` | 📖 glossary | 固定5条模板，我们定义 |

具体做法：evaluator 不输出中文，输出 glossary KEY。和 verdict_engine 一模一样的模式：

```
verdict_engine:    {key: "verdict_product_recommend", params: {...}}
product_evaluator: {labels: ["prod_hot_seller", "prod_high_repurchase"], 
                    human_key: "prod_score_10_12", 
                    score: 12, 
                    data_params: {...}}
```

display_builder 拿到 KEY 后 `_glossary(key, lang)` 查表，拼出目标语言文本。**完全复用现有 `_format_verdict()` 的查表模式。**

## 二、配置策略

**阈值写死在 `product_evaluator.py`，不放 config，不放 glossary。**

理由：阈值是业务规则，不是配置项。verdict_engine.py 也是同样做法——`sold >= 1000`、`years >= 3` 直接写死在 `if` 里。

| 放哪里 | 适合？ | 理由 |
|:--|:--|:--|
| 代码硬编码 | ✅ V1 | 阈值=产品逻辑，改阈值=改产品。和 verdict_engine 一致 |
| config.py | ❌ | 过度设计。阈值不是"环境差异"（dev/prod 不同），是"产品决策" |
| glossary | ❌ | glossary 是翻译数据源，不放业务规则 |

V2 如果要按品类调阈值 → 加一个 `thresholds.json` 放 domain 目录。V1 不搞。

## 三、调用位置

**插入点：`display_builder.py` 的 `build_display()` 函数内。和 verdictProduct/verdictFactory 并列。**

### 现有管线

```
Apify raw → product_mapper.map_raw() → mapped dict
  → display_builder.build_display(mapped, lang)
    → _build_price()
    → _build_trust_bar()
    → ...
    → _format_verdict(mapped.get("verdict_product"))   ← 旧判词
    → _format_verdict(mapped.get("verdict_factory"))   ← 旧判词
    → _format_verdict(mapped.get("verdict_sample"))    ← 旧判词
  → display JSON → 前端
```

### 新管线（只加一行）

```
  → display_builder.build_display(mapped, lang)
    → ...
    → _build_product_eval(mapped, lang)   ← 新增，调 product_evaluator
    → _format_verdict(...)                ← 旧判词保留，不动
```

### 和 verdict_engine 的关系

**并列，不替代。** 旧 verdict 保留（V1 兼容），新 evaluator 输出新的 `productEval` 字段。前端 ② 块读 `productEval`，旧 Tab 页仍然读 `verdictProduct/verdictFactory`。

## 四、主流做法

**"规则引擎即代码"（Rules as Code）——最简单、最主流。**

| 方案 | 例子 | 适合？ |
|:--|:--|:--|
| **规则即代码** | `if sales > 1000: score=3` | ✅ V1。和 verdict_engine 一致 |
| JSON 规则引擎 | `{"condition": "sales > 1000", "score": 3}` | V2 可选。规则多到 50+ 条时考虑 |
| DSL | 自定义规则语言 | ❌ 杀鸡用牛刀 |
| ML 打分 | 训练模型出分 | ❌ 没训练数据，且不可解释 |

本质是 **Martin Fowler 的 "Basic Rules Engine" 模式**。verdict_engine 已经验证过这条路。

- 翻译管线：完全复用 `_glossary()` 查表，函数零改动
