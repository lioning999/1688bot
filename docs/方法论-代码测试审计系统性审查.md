问题一：你怎么保证我改的对，不会引入新问题？
说实话：光改代码，不加验证，我没法保证。 但有三层防线可以把概率压到很低：

第一层：改前写测试，改后跑全量。
现在 tests/ 目录是空的（只有几个残留 import 路径已坏的脚本）。你让我修这 8 个 bug，我每个修完跑一次现有代码的 import 检查 + 对应的 API 调用。但真正的回归测试需要你把应用跑起来，点一遍核心流程（登录→分析→看报告→保存→历史→首页采样）。3 个页面，10 分钟。

第二层：每次改完，跑 /code-review。
这个 skill 会逐行看 diff，找逻辑错误、重复代码、性能问题。它不保证零 bug，但能拦住"改了 A 忘了改 B"这类低级错误。

第三层：改完跑 /verify。
启动应用，实际点一遍。代码看起来对 vs 实际跑起来对，是两回事。

实操建议：8 个 bug 分两批修。 第一批修 B1（持久化）+ open redirect（安全），这两个修复互不依赖，改完立即验证。第二批修剩下的。每批修完你亲自点一遍。这样万一出问题，最多回滚一个批次的改动。

问题二：怎么从根本上防止？
你问了 7 个子问题，我逐个答。

1. "原有代码系统性审查"都审查什么？

检查维度	具体看什么	上次智囊团发现的
安全	输入校验、认证绕过、token 泄漏、SSRF、敏感信息暴露	open redirect、token 在 URL、图片代理 SSRF
性能	重复调用、缓存命中率、内存泄漏、无界循环	Apify 轮换无上限、双重 evaluate
容错	超时处理、降级路径、异常是否被吞、任务悬挂	无硬超时、过期缓存不退配额
数据一致性	标记字段是否统一、缓存与 DB 是否同步	_translatedLang vs _aiGenerated 断裂
死代码	未使用的 import / 函数 / 模块	translate 模块全死
配置漂移	代码实际值 vs 文档 vs 配置文件的差异	缓存 TTL 12h vs 文档 30min
架构合规	是否越层调用、是否违反分层约束	本次没发现
目的不是让代码完美，是让已知风险被看到、被记录、被排期。 看不见的风险才是真正的风险。

2. 审查过了就不会有问题吗？

不会。 审查只能减少问题，不能消灭问题。原因：

静态读代码看不出运行时行为（并发竞态、网络超时、内存压力）
审查的人（我）只能基于当前代码逻辑推断，不能模拟真实用户操作
新功能叠加会改变旧代码的隐含假设（这次 Phase 2 就是典型）
审查 + 测试 + 监控，三者互补：


审查：代码看起来对吗？
测试：代码跑起来对吗？
监控：线上真实用户用起来对吗？
3. 审查和代码审计、测试的区别是什么？

系统性审查	代码审计	测试
谁做	AI（读代码，找模式）	人（安全专家）	AI + 人
看什么	全维度（安全+性能+架构+死代码+配置）	只看安全	只看行为
深度	中等（每文件几分钟）	深（单点几小时）	浅到中等
产出	问题清单 + 优先级	合规报告	通过/失败
什么时候做	每次大改后、新模块上线前	上线前、被攻击后、合规要求	每次改代码
成本	几乎零（AI 跑）	高（人天）	中（写用例）
简单说：审查是"AI 帮你把代码翻一遍，把明显问题捞出来"。审计是"安全专家蹲一周，找一个洞"。测试是"跑一遍看功能炸没炸"。

4. 系统性审查之后还有别的审查吗？

有，按时机分四层：

时机	审查类型	工具
每次提交前	Diff review（只看改动）	/code-review
功能模块完成后	模块 review（该模块所有文件）	智囊团 / 让 AI 逐文件审
上线前	全量安全扫描	/security-review
出事故后	根因分析 + 同类问题排查	/systematic-debugging
你现在缺的是"每次提交前的 diff review"。 这个最便宜、最高频、最能拦住新问题。其他三层按需做。

5. 以前怎么从来没提过？

因为以前的需求是"快速把功能做出来"——Google 登录、Apify 对接、判词引擎、翻译管道、前端页面，一个接一个。每步都是"能不能跑通"，没人问"跑通了但是不是对的、安全的、高效的"。

说白了，项目从 0 到 1 阶段，速度优先。现在到 1 到 N 阶段，质量开始有成本了。 这次智囊团是第一次有人用审查视角扫代码，所以一次性捞出 24 个问题。不是代码突然变差了，是以前没人这么看过。

6. 哪些已安装的 skills 能做？

Skill	能干什么	什么时候用
/code-review	审查当前未提交的 diff，找 bug + 冗余代码	每次改完代码、提交前
/security-review	专门看安全问题（注入、认证、加密、泄漏）	上线前、改认证/支付逻辑后

claude-mem:learn-codebase	一次性扫全仓库建知识图谱	新项目接手时
你现在立刻能用的：/code-review + /security-review。 这两个跑一遍，我上面列的 24 个问题里，至少有一半能被自动标注出来。

我补充老黄没覆盖的一点。

为什么本次新增了 8 个问题？根因就一个：Phase 2 的"完成标准"只有"功能跑通"，没有"对比旧行为，确认无退化"。

具体说：_translatedLang → _aiGenerated 的标记名断裂、双重 evaluate、rankText 漏翻译、translator 变死代码——这四个都是"新功能替换了旧功能的某一部分，但没检查旧功能的调用方是否还依赖被替换的部分"。

以后怎么防：写完新功能后，grep 旧功能的关键字段/函数名，确认所有引用点都适配了。 这是铁律四第 1-3 项的内容，但这次我们只做了 grep 旧名（_build_with_ai → build_with_ai），没做"grep 旧标记字段名（_translatedLang）确认新代码是否覆盖了它的所有使用场景"。

修正铁律四第 1 项的建议：不仅 grep 自己改了什么，还要 grep 自己替换了什么。
