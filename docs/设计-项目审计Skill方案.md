# 项目审计 Skill 设计方案

> 日期：2026-08-08 | 状态：提案
> 背景：pre-flight 设计范围内（单次代码改动的影响面分析）达到 70-80% 有效，但缺少「全项目系统性质量审查」能力。

---

## 一、冲突分析：会不会和现有 skills 打架？

### 1.1 现有审查相关 skills 盘点

| Skill | 范围 | 触发单位 | 核心动作 |
|-------|------|---------|---------|
| **pre-flight** | 单次代码改动 | 一个改动 | grep 影响面 + 两张清单 |
| **review（内置）** | PR diff | 一个 PR | diff 审查 |
| **security-review（内置）** | 待提交更改 | staged files | 安全审查 |
| **simplify（内置）** | 已修改代码 | recent changes | 质量+复用性审查 |

### 1.2 结论：零冲突，各管一档

```
代码粒度假小 ──────────────────────────────→ 大

  security-review    review     simplify    pre-flight    【空缺】    project-audit
  (staged files)    (PR diff)  (recent)    (改动影响面)    (全项目审查)  ← 本方案
```

**每个 skill 的「触发单位」不同：**

| Skill 触发单位 | 你要回答的问题 |
|---------------|--------------|
| security-review | "我这次改动有安全问题吗？" |
| review | "这个 PR 可以合吗？" |
| simplify | "我写的代码够好吗？" |
| pre-flight | "改这个函数会影响哪些地方？" |
| **project-audit（新）** | **"整个项目现在质量怎么样？有什么债？"** |

**不存在功能重叠。** project-audit 填补的是 pre-flight 设计时明确排除的场景（全项目扫描），其他现有 skills 也都不是这个定位。

### 1.3 与 pre-flight 的协作关系

```
pre-flight（战术级）           project-audit（战略级）
├─ 输入：改什么文件、改什么函数   ├─ 输入：审计范围（后端/前端/全项目）
├─ 动作：grep + 两张清单          ├─ 动作：并行 agent × 3 + 按层清单
├─ 输出：影响面报告                ├─ 输出：质量报告 + 修复优先级
└─ 频率：每次改代码前              └─ 频率：每迭代 / 上线前 / 按需
```

两者互补，不互斥。pre-flight 确保改动不出问题，project-audit 确保项目整体健康。

## 二、Skill 设计

### 2.1 基本信息

```yaml
name: project-audit
description: 项目系统性质量审查。触发词：/audit、全项目审查、系统性审计、代码质量审查、项目健康检查。审查整个项目或指定层的架构/安全/性能/文档质量。
```

### 2.2 执行流程

```
步骤0：加载文件地图 + 确认范围

  加载 /file-map → 获取项目文件地图

  问用户 2 个问题（如果已明确则跳过）：
  ① 审查范围？
     □ 全项目（默认）
     □ 仅后端（src/api/）
     □ 仅前端（src/web/）
     □ 仅文档（docs/ + CLAUDE.md）

  ② 审查重点？（可多选，默认 = 全面）
     □ 安全优先
     □ 架构合规
     □ 性能/资源
     □ 文档完整性
     □ 全面（默认）

步骤1：按层并行审查

  启动 3 路并行 agent，每路用独立的审查清单：

  Agent 1: 后端审查
    ├─ 铁律合规（函数行数、命名一致、硬编码、死代码）
    ├─ 安全审计（认证、脱敏、Token、注入、代理）
    ├─ 资源管理（容器上限、定时器清理、连接池、配额）
    ├─ 架构合规（越层调用、循环依赖、模块职责）
    └─ 测试覆盖（测试存在性、旧模块引用、快照失效）

  Agent 2: 前端审查
    ├─ 架构边界（API出口、消息出口、fetch调用）
    ├─ XSS 防御（innerHTML、onclick、URL拼接）
    ├─ i18n 完整性（key覆盖、幽灵语言、msg_code对齐）
    ├─ 状态管理（入口统一、防重入、清理、sessionStorage协议）
    └─ UI 一致性（重复代码、硬编码样式、加载顺序）

  Agent 3: 文档 + 跨层契约
    ├─ 文档索引完整性（README.md 断链、CLAUDE.md 引用）
    ├─ 命名一致性（旧名残留、文件名 vs 文档名）
    ├─ msg_code 覆盖（后端发出 vs 前端翻译）
    ├─ API 契约一致（返回格式、状态码、错误码）
    └─ i18n key 前后对齐

步骤2：汇总 + 去重 + 分级

  合并 3 路结果 →
  ├─ 去重（同一问题被多路发现）
  ├─ 按严重度分级（🔴高 🟡中 🟢低）
  └─ 按优先级排序（立即修 → 本周 → 可延）

步骤3：输出报告

  格式同 docs/审查-全项目Pre-Flight审查报告-20260808.md：
  ├─ 严重度汇总表
  ├─ 🔴 高优先级（必须修）
  ├─ 🟡 中优先级（应该修）
  ├─ 🟢 低优先级（可延后）
  └─ 修复批次建议
```

### 2.3 审查清单（完整版）

#### 后端审查清单

```
铁律合规：
□ 所有 service 方法 ≤50 行？列出超标的
□ 配置值是否硬编码？（超时/配额/缓存参数应走 Config）
□ 命名是否与 CLAUDE.md 一致？
□ 是否有未被引用的死代码？（函数/类/模块）

安全审计：
□ 用户身份是否全部从 request.state 获取？（禁止前端传入）
□ Token/敏感信息是否进日志？
□ 日志脱敏是否实际实现？（对照 CLAUDE.md 承诺）
□ 图片代理重定向是否二次校验？
□ Token 是否进 URL query（会进反向代理日志）？

资源管理：
□ 全局容器（dict/list/queue）有容量上限？
□ setInterval/Task 有清理机制？
□ 后台 task 异常是否被取回？
□ 缓存 TTL + 淘汰机制存在？

架构合规：
□ 是否有越层调用？（routes 直接调 adapters？domain 直接调外部 API？）
□ 是否有循环依赖？
□ 新增模块是否过度设计？（对照铁律三清单）

测试覆盖：
□ 测试文件是否引用已重命名/删除的模块？
□ tests/ 下是否有旧版代码快照？
```

#### 前端审查清单

```
架构边界：
□ 所有 fetch() 是否走 api/core.js？（禁止页面内直接 fetch）
□ 所有 Toast/提示是否走 messages.js？（禁止 alert/手写 toast）
□ API.xxx 方法是否全部存在且被正确使用？

XSS 防御：
□ 所有 innerHTML 赋值前是否过 escHtml()？
□ 是否有 HTML 内联 onclick=？（应统一 addEventListener）
□ URL 参数/用户输入是否直接拼接进 DOM？

i18n 完整性：
□ 前端声明的语言数 vs lang/i18n/ 实际 JSON 匹配？
□ 所有 msg_code 前端 4 语言 JSON 都有 msg.{code}？
□ 有未被使用的死 i18n key？

状态管理：
□ 所有搜索/加载路径是否走统一入口？
□ 是否有全局防重标志？
□ beforeunload 是否清理 timer？
□ sessionStorage key 是否写入 CLAUDE.md 协议表？

代码质量：
□ 是否有明显重复的 DOM 操作逻辑（应抽取为函数）？
□ script 加载顺序是否与 CLAUDE.md 一致？
□ 是否有未使用的 CSS / JS 文件？
```

#### 文档 + 跨层契约清单

```
文档完整性：
□ docs/README.md 中每个索引指向的文件是否真实存在？
□ CLAUDE.md 索引的文档是否全部存在？
□ 每个 .md 文件是否在 docs/README.md 中有索引？

命名一致性：
□ CLAUDE.md 中的文件名是否与磁盘一致？
□ file-map skill 是否与磁盘一致？
□ 旧名（如 report.html）是否在文档中仍有残留引用？

msg_code 对齐：
□ 后端所有 msg_code → 前端 4 语言 JSON 逐一比对
□ 是否存在后端有 code 但前端无翻译？
□ 是否有前端有翻译但后端不再发出的死 key？

API 契约：
□ 所有端点返回格式是否一致（{code, msg_code, data}）？
□ /api/config 是否缺 msg_code？
```

### 2.4 严重度分级标准

| 级别 | 判定标准 | 示例 |
|------|---------|------|
| 🔴 **高** | 安全漏洞 / 数据丢失风险 / 线上 bug / 文档断裂导致开发跑偏 | XSS、文档断链、幽灵语言 |
| 🟡 **中** | 违反铁律 / 维护负担 / 性能隐患 | 硬编码、超长函数、无上限容器 |
| 🟢 **低** | 风格不一致 / 文档漂移 / 可延后优化 | 命名残留、枚举不全、注释过时 |

### 2.5 输出格式

```markdown
# Project Audit 审查报告

> 日期：YYYY-MM-DD | 范围：全项目 / 后端 / 前端
> 依据：根 CLAUDE.md + api/CLAUDE.md + web/CLAUDE.md

## 严重度汇总

| 级别 | 数量 | 说明 |
|------|------|------|
| 🔴 高 | N | 必须修 |
| 🟡 中 | N | 应该修 |
| 🟢 低 | N | 可延后 |

## 🔴 高优先级

| # | 问题 | 位置 | 类别 |
|---|------|------|------|
| 1 | ... | file:line | 安全/架构/文档 |

## 🟡 中优先级
...

## 🟢 低优先级
...

## 修复优先级建议

第1批（本周）：...
第2批（下周）：...
第3批（可延）：...
```

## 三、与现有 skills 的集成

### 步骤0 复用 file-map

```
project-audit 步骤0 = pre-flight 步骤0 的"审查项目"分支
```

不重复造轮子。pre-flight 步骤0 已经区分了"定位文件"和"审查项目"，project-audit 直接走审查分支。

### 可选：pre-flight 步骤0 路由到 project-audit

如果用户说"审查项目"意图足够明确，pre-flight 步骤0 可以提示：

> "这是全项目审查场景，建议使用 `/audit`（project-audit skill），比 pre-flight 更适合。要切换到 audit 吗？"

这不是冲突，是协作——pre-flight 识别自己的边界并引导到正确的工具。

### 与 think-tank 的分工

| | project-audit | think-tank |
|---|---|---|
| 问什么 | "代码现在质量怎么样？" | "这个方案行不行？" |
| 产出 | 具体问题清单 + 位置 + 修法 | 多角度观点 + 决策建议 |
| 输入 | 代码库本身 | 想法/方案/需求 |

## 四、实施建议

### 4.1 Skill 文件位置

```
.claude/skills/project-audit/
└── SKILL.md          (~200 行)
```

### 4.2 触发词设计

**主触发词：** `/audit`
**自然语言触发：** 全项目审查、系统性审计、代码质量审查、项目健康检查、查查代码质量、帮我审一下项目

### 4.3 与 pre-flight 的触发词区分

| 用户说 | 触发 |
|--------|------|
| "改前检查""影响面分析""/pre-flight" | pre-flight |
| "/audit""全项目审查""系统性审计""代码质量""项目健康" | project-audit |
| "排查XX问题" | file-map（定位）或 直接进排查流程 |

### 4.4 可选的快速模式

用户说 `/audit --quick` 或"快速审查"时：
- 跳过全面扫描
- 只检查 🔴 级安全问题 + 架构违规
- 3 分钟内出结果

## 五、已知限制

1. **不替代 CI/CD 静态分析。** project-audit 是 AI 驱动的语义级审查，无法替代 lint、type check、SAST 等确定性工具。
2. **不替代安全渗透测试。** 只能审查代码模式，不能模拟攻击。
3. **文档断裂检查依赖 docs/README.md 准确性。** 如果索引本身就错，需要人工介入。
4. **大型项目（>200 文件）** 全量审查需要较长时间（~2-5 分钟），建议日常用按层审查，上线前才做全项目。
